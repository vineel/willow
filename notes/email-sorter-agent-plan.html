Foldersort agent — rules and classifiers conceptual model

Context

Vineel wants a new Willow agent that sorts incoming Fastmail messages out of the inbox into subfolders. Mechanically: deterministic rules first, LLM judgment (LM Studio / google/gemma-4-e4b) on everything else. Conceptually: the catalog of rules and folder definitions must be growable by talking to Willow — same way willow-triage and willow-interests already grow.

Key framing decisions (confirmed with user):

  • Targets are subfolders of an existing willow-secondary folder in Fastmail, not arbitrary mailboxes. The inbox is the "important stuff" set; sorting = moving things away from the inbox into the right subfolder.
  • "Leave in inbox" is the dominant outcome, not an edge case. The classifier should err on the side of leaving things in place.
  • Backfill is a v0 deliverable: 1-day backfill for testing, then 7-day backfill once ready. CLI driven, proposal-only.
  • Source of truth for rules is table-backed (folder_profile + folder_rule), with prose-feeling MCP edits.

He has prior notes at ~/aidev/willow/working-on-spam-filter.md with strong staged-rollout discipline ("moving/deleting email is irreversible-feeling"). The current pipeline is read-only — this will be Willow's first write-back-to-mail capability.

This plan covers the full v0 build (rules + classifier + bootstrap + dry-run + backfill + proposal mode). Approval/auto-apply phases and daily-sweep are referenced but deferred to post-v0.

The three concepts

1. Folder profile — the catalog entry per folder

The LLM can't pick a folder it doesn't know about. Each subfolder of willow-secondary gets a profile — a small natural-language record that teaches the LLM what belongs there. Profiles are the source of truth for the folder taxonomy.

Shape (DB-backed but prose-feeling in MCP tools):

CREATE TABLE app.folder_profile (
  name              text PRIMARY KEY,        -- subfolder leaf name under willow-secondary
  mailbox_id        text,                    -- resolved JMAP id; refreshed on bootstrap
  parent_path       text DEFAULT 'willow-secondary',
  description       text NOT NULL,           -- one-line shown to LLM
  llm_hint          text,                    -- longer guidance, optional
  example_subjects  text[] DEFAULT '{}',     -- corrective-feedback exemplars
  example_senders   text[] DEFAULT '{}',     -- ditto
  enabled           boolean DEFAULT true,
  created_at        timestamptz DEFAULT now(),
  updated_at        timestamptz DEFAULT now()
);

mailbox_id is cached for fast move-application; refresh on bootstrap / mailbox-not-found error. Reasoning for table-not-markdown: matches app.interest (description + keywords[] + action_prompt) — already-proven shape for mixing prose and structure. The MCP UX still feels prose-y: create_profile(name, description, llm_hint) reads exactly like dictating a paragraph.

2. Folder rule — deterministic shortcut

For the obvious cases ("everything from spotify.com → Subscriptions") the LLM is overkill. A folder_rule table parallel to triage_rule uses the same field/operator vocabulary and engine, but its action is always "move to folder X":

CREATE TABLE app.folder_rule (
  id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  name            text NOT NULL,
  field           text NOT NULL,          -- same as triage_rule
  operator        text NOT NULL CHECK (operator IN ('equals','contains','starts_with','ends_with','regex','exists','gte')),
  value           text,
  header_name     text,
  target_folder   text NOT NULL REFERENCES app.folder_profile(name),
  priority        integer DEFAULT 100,
  enabled         boolean DEFAULT true,
  confirmed       boolean DEFAULT false,
  source          text NOT NULL CHECK (source IN ('system','user','agent')),
  created_at      timestamptz DEFAULT now(),
  updated_at      timestamptz DEFAULT now()
);

Reuse matchOperator() and extractFieldValue() from pib/triage/engine.ts:9-80 directly — they're field-agnostic. Same first-match-wins semantics.

Why a parallel table instead of extending triage_rule: triage_action (noise|digest|queue|flag) and target_folder are orthogonal decisions. A message can simultaneously be triage_action=queue AND target_folder=Receipts. Conflating into one engine means a queue rule below a move_to_folder rule never fires. Kept separate, both engines run cleanly.

3. Decision record — column on fact, not a new table

The "what did we decide for this email" record lives as columns on app.fact, mirroring the existing triage_action/triage_source/triage_rule_id pattern at db/schema.sql:103:

ALTER TABLE app.fact ADD COLUMN folder_target text;
ALTER TABLE app.fact ADD COLUMN folder_decided_by text CHECK (folder_decided_by IN ('rule','llm','default','skip'));
ALTER TABLE app.fact ADD COLUMN folder_rule_id uuid REFERENCES app.folder_rule(id);
ALTER TABLE app.fact ADD COLUMN folder_proposed_at timestamptz;
ALTER TABLE app.fact ADD COLUMN folder_applied_at timestamptz;
ALTER TABLE app.fact ADD COLUMN folder_error text;

Co-locates triage and foldersort decisions; lets the digest section "what got proposed today" be one query.

The classifier (LLM as judge)

Copy the prompt pattern from pib/classify.ts:50-86 directly. The only thing that changes is the taxonomy:

  1. Load enabled folder profiles. Expected count is small (~10-20 subfolders under willow-secondary) — no prefilter needed for v0. Revisit if the count grows past ~25.
  2. leave_in_inbox is always in the enum AND is the explicit default. Prompt should say "If you are not confident a message belongs in one of these folders, choose leave_in_inbox. The inbox is for important and uncategorized mail; it is correct to leave a lot of mail there."
  3. Format profiles one-line each (Receipts: order confirmations, shipping notices, store purchase receipts). NO example_subjects in the prompt body — those grow via corrective feedback but don't go to LLM at decision time, to keep the prompt short.
  4. Pass through chatCompletion() (memory/lmstudio/client.ts) with strict json_schema requiring { selected_folder: string, reason: string }. The schema's enum is profile_names + ["leave_in_inbox"]. Gemma cannot emit anything else. reason is a one-sentence rationale captured in the decision log for review.
  5. temperature: 0.1 (same as pib/classify.ts:107).

Confidence is intentionally ignored — local Gemma always reports 0.9. The single gate is enum validity (tautological under strict schema). The conservative-default bias is built into the prompt, not the gating logic.

Growth-by-conversation — three mechanisms

The whole point of this design is the catalog grows by talking to Willow. A new MCP server willow-foldersort exposes these tools (mirroring willow-triage / willow-interests shape):

A. Add a folder profile

"I made a folder called Receipts. It's for order confirmations, shipping notices, and store purchase receipts."

→ create_profile(name="Receipts", description="order confirmations, shipping notices, store purchase receipts", llm_hint=null).

Verify the named folder exists in Fastmail (getMailboxes() from pib/jmap/session.ts:42). If not, surface the mismatch — don't auto-create folders.

B. Add a deterministic rule

"Always put email from spotify.com into Subscriptions."

→ add_folder_rule(field="from_domain", operator="equals", value="spotify.com", target_folder="Subscriptions", source="user", priority=1).

The rule from a specific Fastmail URL is the most ergonomic flow. The recently-built fastmail-mcp.fetch_email(url) (Bridge POST /mail/get) gives us subject + from + headers from a single URL. Mirror it: add_folder_rule_from_url(url, target_folder, kind="sender"|"domain"|"subject_contains") resolves the URL, extracts the matching field, creates the rule.

C. Correct a misplacement

"This went to X but should have gone to Receipts." (paste URL or reference fact_id)

→ correct_placement(email_ref, target_folder, reason?) runs this decision tree against the fact row:

  1. If folder_decided_by='rule' → the rule mis-fired. Set the offending rule enabled=false (demote, don't delete — easier to recover) AND add the email's subject/sender to the correct profile's example_subjects/example_senders.
  2. If folder_decided_by='llm' AND this sender has been corrected toward the same target ≥3 times in the last 90 days → write a new high-priority folder_rule (from_address equals X → target), source='agent', confirmed=true.
  3. If folder_decided_by='llm' (sporadic) → append to example_subjects on the target profile only. No new rule.
  4. If folder_decided_by='default' → either prompt to create_profile (target doesn't exist) or append exemplars.

llm_hint is updated only on explicit user instruction (update_profile(name, llm_hint=…)), never on individual corrections — avoids hint drift from one-off cases.

After applying the corrective record, re-run foldersort against a fresh fetch of the same email (dry-run only) to confirm the next decision would be correct.

Chat-driven preview-and-correct flow

preview_inbox_sort(count=20, source="recent_ingested" | "since_last_preview") returns a compact text block formatted for in-chat display: N recent inbox emails with their proposed sort destination, the reasoning, and a fact_id short reference for follow-up corrections.

Output shape (one block per email, easy to scan in Claude Code / Codex chat):

#1  [fact:7c4a]   2026-05-23
    From:     Amazon.com <auto-confirm@amazon.com>
    Subject:  Your Amazon order has shipped: "kindle paperwhite"
    →         uninteresting   (rule:amazon-shipping)

#2  [fact:a39e]   2026-05-23
    From:     Nate B. Jones <nate@natebjones.substack.com>
    Subject:  The unbundling of search and the new content economy
    →         my-reading      (rule:substack-nate)

#3  [fact:4d11]   2026-05-23
    From:     Mary Smith <mary.smith@gmail.com>
    Subject:  Are you free Saturday?
    →         leave_in_inbox  (llm: appears to be personal correspondence;
                              sender is in the known correspondent list)

…

Corrections in the same chat conversation:

"Change #3 to people-i-don't-know" → agent calls correct_placement(fact_id="7c4a-…full", target_folder="people-i-don't-know") against the underlying fact.

Or by reference to the email:

"Move the Amazon one to leave_in_inbox" → agent resolves "the Amazon one" to fact_id from the preview output, then calls correct_placement.

The preview output also writes proposals to the fact row (same columns as backfill) so subsequent listings don't repeat the same emails — that's the source="since_last_preview" default once a previewed_at column is added. For v0 simplicity, source="recent_ingested" (default 20 most recent ingested-but-not-yet-proposed inbox messages) is fine.

Mirrored CLI: bun run foldersort:preview -- --count 20 prints the same blocks to terminal. Useful for spot-checks outside chat.

Bootstrap flow (v0)

bun run foldersort:bootstrap does the following, idempotently:

  1. JMAP-fetch all mailboxes (extending getMailboxes() to also return parentId).
  2. Find the willow-secondary mailbox by name.
  3. Enumerate its direct children.
  4. For each subfolder: upsert a row into folder_profile with name=<leaf name>, mailbox_id=<jmap id>. Existing description / llm_hint / examples are preserved.
  5. On first run, seed descriptions from the seed-taxonomy table below (so the user doesn't have to hand-fill them). On subsequent runs, only add new folders; don't overwrite edits.
  6. Print a table of profiles with empty descriptions for the user to fill in via update_profile MCP.

This handles renames/moves too: re-running picks up the latest mailbox_id and any new subfolders.

Seed taxonomy (v0)

The bootstrap script seeds these descriptions on first run. The user's update_profile MCP can refine them at any time. Seed senders are inserted as example_senders and also become high-priority folder_rule rows (source='system', confirmed=false) so they fire deterministically without burning an LLM call.

Profile Seed description (LLM prompt line) Seed senders → rules Notes
uninteresting repeated transactional emails, marketing from companies the user does not care about, generic notifications, mundane stuff (none — LLM only) catch-all; LLM should still prefer leave_in_inbox if uncertain
marketing-interesting marketing about things the user might care about — concerts, AI lab updates, music/movie festivals, books, niche commerce spotify.com, anthropic.com, openai.com, visasq.com, zenni.com; amazon "Top Kindle Books" subject pattern amazon.com is split: kindle/recommendation subjects here, order confirmations should stay in inbox or land in uninteresting
zeph-college college and university outreach to Zeph or any student in the household — admissions, campus visits, applications (none) LLM should look for .edu domains + admissions/college language
maybe-spam likely spam, political outreach, PAC and campaign mail (none) overlaps with triage noise action; foldersort still proposes here so the user can review rather than silently discarding
my-reading newsletters and reading-list content the user reads regularly — Substack, Business Insider, Alley Watch substack.com (specifically Nate B Jones), businessinsider.com, alleywatch.com many substacks come from custom domains; rules will need iterative expansion
people-i-don't-know mail from an actual individual person whom the user hasn't corresponded with recently (none — heuristic only) see v0 limitation below
vineel-curated (managed externally by a Fastmail rule on To: curated@vineel.com) n/a disabled in the foldersort enum — never an LLM target

Special handling

  1. vineel-curated is excluded from the LLM enum. A Fastmail server-side rule already routes mail addressed to curated@vineel.com here. The profile exists in the DB for completeness but is created with enabled=false. The LLM never sees it as an option; foldersort decisions are blind to it. Mail that Fastmail already routed there won't enter the inbox in the first place.

  2. people-i-don't-know uses a sent-mail correspondent list as the primary signal. The strict semantic — "actual individual, not responded to in the last year" — is supported by a maintained correspondent list (see next section). The foldersort decision flow then becomes:

    • Sender appears to be an individual (has a plausible person-name, not "noreply"/"updates"/etc., no List-Unsubscribe header).
    • from_address is NOT in the correspondent list (the strong signal).
    • LLM prompt is told this is the rule and given the freedom to fall back to leave_in_inbox if the message is clearly important regardless.
    • Maintenance: an initial one-year bootstrap scan + a daily incremental scan keep the list fresh automatically. A manual MCP tool lets Vineel whitelist new contacts on demand ("I know brent@wakes.com now").

Sent-mail correspondent list (v0)

app.correspondent is the source of truth; ~/aidev/willow/data/correspondents.txt is an auto-regenerated audit artifact (sorted dump of every address in the table) refreshed after every scan and after every manual add/remove.

-- Added to migration 012
CREATE TABLE app.correspondent (
  address      text PRIMARY KEY,
  source       text NOT NULL CHECK (source IN ('scan','manual')),
  note         text,                          -- optional: why this was added manually
  first_seen   timestamptz DEFAULT now(),
  last_seen_at timestamptz DEFAULT now()      -- bumped each time the scan re-encounters the address
);

Bootstrap scan (one-time)

bun run foldersort:scan-sent -- --since 365d does:

  1. JMAP-fetch sent mailbox (role='sent').
  2. Email/query with filter: { inMailbox: <sent_id>, after: <iso N days ago> }, paginated.
  3. For each batch, Email/get with properties: ["to","cc","bcc","sentAt"].
  4. Extract all addresses from to + cc + bcc, lowercase, dedupe.
  5. Upsert into app.correspondent with source='scan', bumping last_seen_at on existing rows.
  6. Regenerate the audit file from SELECT address FROM app.correspondent ORDER BY address.
  7. Print a count summary (Upserted N addresses, M new; file now has K lines).

Daily incremental scan (cron)

Same script, run with --since 2d from a new Graphile Worker cron task (registered in pib/worker.ts):

  • Schedule: daily at 04:30 ET (before the 6:45 ET digest)
  • Why 2 days: cheap overlap to absorb missed runs / DST quirks / clock drift; the JMAP fetch is small at this scale
  • Effect: any address Vineel sent mail to on day N is upserted to the correspondent table by day N+1's run. From day N+1's incoming mail onward, the sender is treated as known and stays in inbox by the people-i-don't-know heuristic.

This delivers the user's "second day" semantic: emailing someone today → they're in the whitelist tomorrow morning, so their replies don't get routed away.

Manual whitelist via MCP

Two new MCP tools (in willow-foldersort):

  • add_correspondent(email, note?) — immediate upsert with source='manual'. Use case: "I know brent@wakes.com now" → agent calls add_correspondent("brent@wakes.com", "met at conference"). Brent's next incoming email finds him in the list and stays in inbox.
  • remove_correspondent(email) — delete from table. Use case: "I don't actually know this person, take them off" (covers cases where the scan picked up an automation address that shouldn't grant trust, like 82700857702227032042668224308989ver2@mg.upwork.com).
  • list_correspondents(contains?) — filtered listing for inspection.

All three regenerate the audit file synchronously after mutating the table.

Splitting responsibilities

  • The DB is the runtime index — fast EXISTS check during decide.
  • The file is the audit artifact — user can cat / grep / sort. Never edited by hand (changes get clobbered on next regen); manual changes go through add_correspondent / remove_correspondent MCP.
  • The bootstrap-vs-daily split keeps the slow first scan separate from the cheap incremental ones, but both go through the same code path.

Backfill flow (v0)

bun run foldersort:backfill -- --days N (default --days 1):

  1. Pull last N days of inbox messages from app.fact joined to app.source_note (already-ingested emails only — no JMAP re-fetch).
  2. For each, run decide(fact, profiles, rules) to produce { target, decided_by, reason }.
  3. Write folder_target, folder_decided_by, folder_proposed_at to the fact. No JMAP move.
  4. Print summary: "Proposed: 23 → Receipts, 8 → Subscriptions, 4 → Bills, 67 → leave_in_inbox".
  5. Emit a one-line digest entry per proposed move for review.

User runs --days 1 first to spot-check; once happy, --days 7 for the broader pass.

Rollout phases (from user's prior notes; binding)

Phase 1 (v0) — proposal-only. Pipeline writes folder_target + folder_proposed_at to the fact; does NOT call any JMAP move. Daily digest grows a section: "I would move 47 emails: [list with target + reason]." Vineel approves via a Gizmo or by calling an MCP tool. On approval, the dispatch worker calls moveEmail() and stamps folder_applied_at. No auto-execution in v0.

Phase 2 (post-v0) — per-rule confidence threshold. Once a folder_rule has 20+ proposals approved with zero rejections, flip an auto_apply flag on that rule. LLM-driven decisions stay proposal-only.

Phase 3 (post-v0) — full auto with weekly audit.

The migration supports all three: folder_proposed_at vs folder_applied_at are separate columns; apply.ts is a separate function only invoked by approval flow, not by the pipeline directly.

Open questions surfaced to user

From working-on-spam-filter.md and the architecture decision:

  1. Source of truth shape: structured per-folder rows (this plan) vs. a single growing markdown doc (organize-rules.md) fed as system prompt?
  2. Initial taxonomy: bootstrap profiles from existing Fastmail folders (via getMailboxes()) and ask the user to describe each, vs. design fresh?
  3. Backfill: organize inbox going forward only, vs. one-time pass over historical inbox? Big stakes implication for proposal-mode review volume.
  4. Delete semantics: when a rule says "delete" (out of scope for v0 but coming), Email/set destroy vs move to Trash? Latter much safer.

These should be answered before implementation begins; (1) and (2) shape the schema, (3) shapes the digest UX, (4) is deferrable.
